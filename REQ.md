## 1. Назначение, цели и границы

### 1.1. Назначение
Модуль централизованно хранит и версионирует составы изделий компании и формирует из них состав конкретного изделия (100% BOM) для производства.

### 1.2. Цели
1. Единый реестр артикулов `xxY.zz.nnnnn` с автоматической выдачей номеров без дублей.
2. Хранение ревизий составных частей вместе с файлами. Утверждённая ревизия неизменяема.
3. Импорт составов сборок из КОМПАС-3D и электрических составов из QElectroTech (схемы) и Altium (платы) — с релизных тегов их git-репозиториев, — а также из универсального CSV/JSON. Ручной ввод спецификаций исключён.
4. Описание продукта как 150% BOM: все модули и варианты плюс правила применимости по опциям и датам.
5. Получение 100% BOM на дату для заданного набора опций.

### 1.3. Границы (что НЕ входит в MVP)
- Процедуры ECR/ECO с многосторонним согласованием и анализ влияния изменений — этап 3 (§13). Модель данных их предусматривает.
- Серийные номера и фактический состав изготовленного экземпляра (as-built), применимость по серийному номеру — этап 4.
- Check-out/check-in файлов и открытие сборок КОМПАС напрямую из хранилища системы — этап 4.

## 2. Термины

| Термин | Определение |
|---|---|
| Артикул (SKU) | Бизнес-ключ составной части вида `xxY.zz.nnnnn` (§4). Неизменяем. |
| Мастер-запись | Сущность «составная часть» с артикулом. Не зависит от ревизий. |
| Ревизия | Версия составной части (`01`, `02`…): файлы и, для составных типов, состав. |
| Состав (структура) | Перечень входящих позиций с количествами. |
| 150% BOM | Состав продукта P, содержащий все возможные модули и варианты с правилами применимости. |
| 100% BOM | Состав, полученный из 150% BOM для конкретного набора опций на конкретную дату. |
| Опция | Логический признак комплектации продукта (`WINTER_PACK`, `CHIP_V2`). |
| Правило применимости | Булево выражение над опциями, при котором позиция входит в 100% BOM. |
| Применимость по дате | Интервал `[valid_from, valid_to)`, в котором действует позиция состава продукта. |
| FFF | Fit, Form, Function — критерий взаимозаменяемости (§6.2). |
| MCAD / ECAD | Источник данных: механическая CAD-модель или электрическая схема / плата. |
| RefDes | Позиционное обозначение элемента на схеме (`M1`, `R15`). |
| MPN | Артикул производителя покупного изделия (part number); для крепежа и стандартных изделий без part number — обозначение по стандарту (`DIN 912 M3x10 A2`). В КОМПАС — свойство «Код продукции», в QElectroTech — поле Article number, в Altium — колонка Part. |
| Компонент каталога | Любое покупное изделие без доработки — крепёж, материал, мотор, датчик, резистор, автомат, клемма, — идентифицируемое по MPN, без собственного артикула `xxY.zz.nnnnn`. |
| Позиция | Артикул или компонент каталога в составе. |
| Релиз | Тег git-репозитория схемы или платы, отмечающий утверждённую автором документацию. Ревизия E/B создаётся из релиза. |

## 4. Конвенция артикулов

Маска артикула — **xxY.zz.nnnnn**:
* **xx** — префикс проекта / кампании `[A-Z]{2}`.
* **Y** — тип составной части:
  * `P` — продукт (изделие целиком, имеет серийный номер);
  * `A` — сборка (механический CAD-узел);
  * `D` — детали (механические элементы без подключения проводов);
  * `E` — электрика (схемы и собственные электротехнические изделия; покупные датчики, кнопки, моторы — компоненты каталога);
  * `B` — платы (печатные платы с топологией);
  * `C` — кабели (кабельные сборки и жгуты);
  * `G` — мануалы (инструкции и документация).
* **zz** — группа составных частей `[A-Z0-9]{2}`.
* **nnnnn** — порядковый номер `00000…99999`.

- **REQ-ART-01.** Артикул вычисляется СУБД из составляющих (`GENERATED ALWAYS AS`), допускается только латиница. Ввод кириллических двойников (`С`, `В`, `А`, `Е`…) отклоняется с явным сообщением о том, какой символ кириллический.
- **REQ-ART-02.** Проекты (`xx`) и группы (`zz`) ведутся в справочниках с описаниями. Группа — классификатор **внутри типа**: справочник групп ведётся по паре (проект, тип), поэтому `GAD.32` и `GAE.32` — разные группы со своими названиями. Создать артикул в несуществующем проекте или группе нельзя.
- **REQ-ART-03.** Номер `nnnnn` выдаёт система: наименьший **свободный** номер тройки (проект, тип, группа), начиная со счётчика. Занятые номера, в том числе созданные вручную (REQ-ART-04), генератор пропускает. Выдача атомарна (блокировка строки счётчика), параллельные запросы не получают одинаковый номер. Номера не переиспользуются, даже если артикул удалён (REQ-ART-05).
- **REQ-ART-04.** Администратор может создать артикул с явно указанным номером, когда у изделия уже есть артикул (нанесён на деталь или стоит в «Обозначении»; см. REQ-MIG-02). Счётчик при этом **не сдвигается**: номера ниже заданного остаются доступны генератору, а сам заданный номер генератор пропустит. Пример: счётчик `GAA.GF` на `00003`, вручную создан `00534` → генератор выдаёт `00003` … `00533`, затем `00535`. Занятый номер — ответ `CONFLICT`. Создание с ручным номером записывается в журнал с пометкой «номер задан вручную» и, как и генератор, блокирует строку счётчика.
- **REQ-ART-05.** Артикул после создания не меняется. Удалить можно только артикул без утверждённых ревизий, который нигде не используется. Удаление логическое (`deleted_at`): запись остаётся в реестре и занимает номер, артикул скрывается из поиска и не допускается в составы.
- **REQ-ART-06. Правила вложенности.** Допустимые типы потомков в составе:

| Родитель      | Допустимые потомки | Источник состава                                                |
| ------------- | ------------------ | --------------------------------------------------------------- |
| P (продукт)   | A, B, C, E, G      | ручное редактирование в системе (§7)                            |
| A (сборка)    | A, D, E, B, C, G   | импорт MCAD + ручные позиции                                    |
| E (электрика) | E, B, C, D         | импорт QElectroTech + ручные позиции |
| B (плата)     | B, E               | импорт Altium + ручные позиции                                  |
| C (кабель)    | E, D               | импорт / ручные позиции (разъёмы, провод в метрах)              |
| D (деталь)    | — (лист)           | —                                                               |
| G (мануал)    | — (лист)           | —                                                               |

  Компоненты каталога допускаются в составе любого типа, кроме P. Нарушение правил вложенности — ошибка при импорте и при ручном редактировании.
- **REQ-ART-07. Граница «свой артикул / каталог».** Собственный артикул получают только изделия, которые мы разрабатываем или дорабатываем. Покупные изделия без доработки (крепёж, материалы, моторы, датчики, электронные компоненты) собственного артикула не получают и учитываются как компоненты каталога (REQ-ART-08) — и в MCAD, и в ECAD. Доработанное покупное изделие (например, мотор с проточенным валом) — собственный артикул со ссылкой на исходный компонент (`base_component`).
- **REQ-ART-08. Компоненты каталога.** Каталог хранит покупные изделия по MPN с описанием, изготовителем, единицей измерения, аналогами и атрибутами источника (Footprint, Comment, JLCPCB Part). Признак «мехатроника» ставится автоматически, когда компонент впервые встречается в импорте MCAD (его можно изменить вручную); он используется для проверок склейки (§8.6). 3D-модели покупных изделий в системе не хранятся — они в библиотеке компонентов КОМПАС. Материалы (провод, клей) заводятся в каталоге заранее, с единицей измерения.
- **REQ-ART-09. Уникальность MPN.** Нормализованный MPN (без пробелов по краям, в верхнем регистре) уникален в каталоге независимо от производителя: производитель — справочный атрибут, а не часть ключа (в BOM Altium его нет). Одно и то же покупное изделие в MCAD и ECAD — один компонент каталога, поэтому склейка (§8.6) идёт по MPN напрямую.

## 5. Модель данных

Полный DDL — в [Приложении A](#Приложение%20A.%20DDL%20(PostgreSQL)). Принципы:
- **Суррогатные ключи** (`*_id`) для связей, **артикул** — бизнес-ключ для людей и API.
- **Два режима версионирования состава** (решение D5):
  - составы A, B, C, E **заморожены в ревизии** (`structure_line`): изменение состава — это новая ревизия;
  - состав продукта P версионируется **датами применимости** (`product_line`), а его ревизии содержат только документацию.
- **История не удаляется:** утверждённые данные и прошедшие интервалы применимости не изменяются (§6, §7).

### 5.1. Сущности

| Сущность | Назначение | Ключевые атрибуты |
|---|---|---|
| `project` | Справочник проектов `xx` | код, название |
| `item_group` | Справочник групп `zz` по типу в проекте | проект, тип, код, название |
| `item_counter` | Счётчик номеров по тройке | проект, тип, группа, `next_number` |
| `item_master` | Составная часть (собственное изделие) | составляющие артикула, `display_sku`, наименование, ед. изм., исходный компонент (для доработанных покупных), git-репозиторий (для E/B) |
| `component` | Компонент каталога (REQ-ART-08) | MPN, описание, изготовитель, ед. изм., аналоги, признак «мехатроника», атрибуты источника (JSONB) |
| `item_revision` | Ревизия | код `01..99`, статус, комментарий, номер извещения, создал / утвердил, даты; для E/B — репозиторий, тег, commit, параметры (JSONB, например `board_options`) |
| `revision_file` | Файлы ревизии | имя, роль файла, ключ в хранилище, SHA-256, размер |
| `structure_line` | Позиция состава ревизии A/B/C/E | ревизия-родитель, потомок (артикул **или** компонент каталога), количество, источник, массив RefDes |
| `product_line` | Позиция 150% состава продукта P | продукт, потомок, количество, правило, `valid_from`, `valid_to`, номер извещения |
| `option_group` | Группа опций с ограничением | продукт, код, режим `ANY / AT_MOST_ONE / EXACTLY_ONE` |
| `product_option` | Опция продукта | продукт, код, название, группа, активна |
| `configuration` | Именованный набор опций (комплектация / заказ) | продукт, имя, список опций, ссылка на заказ |
| `app_user` | Пользователь | логин, ФИО, роли, хеш API-токена |
| `audit_log` | Журнал | кто, когда, сущность, действие, данные (JSONB) |

### 5.2. Инварианты
- **REQ-DM-01.** На артикул существует не более одной ревизии в статусе In_Development.
- **REQ-DM-02.** Позиции состава и файлы ревизии в статусе Approved/Obsolete нельзя добавлять, изменять или удалять. Это обеспечивает триггер СУБД, а не только backend.
- **REQ-DM-03.** В `structure_line` у позиции заполнен ровно один из двух потомков: артикул или компонент каталога. Один потомок встречается не более одного раза на пару (ревизия, источник). Экземпляры агрегируются в количество, позиционные обозначения — в массив `ref_des`. Это заменяет PK `(parent_rev_id, child_id, valid_from)` из черновика, который не позволял хранить строки MCAD и ECAD одного потомка.
- **REQ-DM-04.** Количество > 0. Единица измерения берётся из потомка — артикула или компонента (`шт`, `м`, `кг`, `м2`, `л`). Единица «комплект» не вводится: набор (например, крепёж к узлу) оформляется сборкой A со своим составом. Если источник прислал для потомка другую единицу измерения, это ошибка импорта.
- **REQ-DM-05.** Состав не может содержать циклов (A1 → A2 → A1). Проверка выполняется при утверждении и при импорте.
- **REQ-DM-06.** Все даты хранятся как `TIMESTAMPTZ`.
- **REQ-DM-07.** Каскадное удаление между мастер-записями, ревизиями и составами запрещено. Каскад допускается только при удалении черновой ревизии.

## 6. Жизненный цикл

### 6.1. Статусы ревизии

```
 (создание) ──► In_Development ──[Утверждающий]──► Approved ──[утверждена следующая]──► Obsolete
                     │
                     └──[удаление черновика]──► ∅
```

- **REQ-LC-01.** Новая ревизия создаётся как копия последней утверждённой: файлы-ссылки и позиции состава копируются. Код ревизии — следующий двузначный номер.
- **REQ-LC-02.** При утверждении новой ревизии предыдущая Approved автоматически становится Obsolete.
- **REQ-LC-03.** Статус Obsolete означает «заменена», а не «запрещена». Такие ревизии продолжают участвовать в расчёте состава на прошлые даты (§7.4).
- **REQ-LC-04.** Возврат Approved → In_Development невозможен. Исправление делается новой ревизией.

### 6.2. Новая ревизия или новый артикул (правило FFF)
- **Новая ревизия** (артикул не меняется): деталь изменена, но полностью взаимозаменяема со старой — материал клея, скругление, уточнение чертежа, перерисовка без изменения посадочных мест.
- **Новый артикул** обязателен при потере взаимозаменяемости: изменились габариты, точки крепления, интерфейс разъёма, критические электрические параметры.
  - Если меняется позиция продукта P, старая позиция `product_line` закрывается датой (`valid_to = T`), а новая добавляется с `valid_from = T` (§7.2).
  - Если меняется позиция внутри сборки, создаётся новая ревизия сборки с новым потомком.
- **REQ-LC-05. Распространение вверх.** Если новый артикул детали делает невзаимозаменяемой и сборку, конструктор присваивает новый артикул и сборке. Решение принимает инженер, а система помогает отчётом «где используется» (§9.2) с полной цепочкой родителей до продуктов P.
- **REQ-LC-06.** В UI при создании ревизии и артикула показывается напоминание о правиле FFF, а в комментарии ревизии требуется указать причину изменения.

### 6.3. Утверждение в MVP
- **REQ-LC-07.** В Approved переводит пользователь с ролью «Утверждающий». Он указывает комментарий и, необязательно, номер извещения — свободное поле до появления ECO на этапе 3.
- **REQ-LC-08.** Утверждение отклоняется, если:
  - (а) у ревизии нет ни одного файла;
  - (б) состав содержит потомков, у которых нет ни одной ревизии;
  - (в) нарушены правила вложенности или обнаружен цикл.
- **REQ-LC-09.** Каждый переход статуса записывается в `audit_log`.

## 7. Опции, применимость и конфигуратор (150% → 100%)

### 7.1. Опции
- **REQ-OPT-01.** Словарь опций ведётся отдельно для каждого продукта P. Код опции: `^[A-Z][A-Z0-9_]*$`, кроме зарезервированных `AND`, `OR`, `NOT`.
- **REQ-OPT-02.** Опции объединяются в группы с режимом:
  - `ANY` — без ограничений;
  - `AT_MOST_ONE` — не более одной (например, вариант крышки);
  - `EXACTLY_ONE` — ровно одна (например, вариант шасси).
- **REQ-OPT-03.** Опцию, которая используется в правилах, нельзя удалить. Её можно только деактивировать: она останется в истории, но не будет предлагаться для новых конфигураций.

### 7.2. Позиции продукта и применимость по дате
- **REQ-PL-01.** Позиция продукта — это (потомок, количество, правило применимости, `valid_from`, `valid_to`). `valid_to = NULL` означает «действует до сих пор». Интервал полуоткрытый: `[valid_from, valid_to)`.
- **REQ-PL-02.** Позиции, действовавшие в прошлом, не редактируются и не удаляются. Изменение делается закрытием (`valid_to`) и добавлением новой позиции. Позицию с `valid_from` в будущем можно редактировать и удалять.
- **REQ-PL-03.** `valid_from` новой позиции не может быть раньше текущего момента. Исключение — администратор, при миграции и с записью в журнал.
- **REQ-PL-04.** Операция «Заменить позицию» в одной транзакции закрывает старую позицию и открывает новую с той же датой `T`. Правило и количество переносятся с возможностью изменить их.
- **REQ-PL-05.** Каждое изменение `product_line` записывается в `audit_log` с номером извещения, если он указан.

### 7.3. Правила применимости
- **REQ-RULE-01.** Грамматика — в [Приложении C](#Приложение%20C.%20Грамматика%20правил%20применимости): идентификаторы опций, `and`, `or`, `not` (без учёта регистра) и скобки. Пустое правило означает, что позиция входит всегда.
- **REQ-RULE-02.** Правило разбирается собственным парсером по белому списку. Использовать `eval`/`exec` запрещено: вариант черновика с `{"__builtins__": None}` обходится через `().__class__.__base__.__subclasses__()`.
- **REQ-RULE-03.** Правило проверяется **при сохранении**: синтаксис и существование всех опций в словаре продукта. Некорректное правило не сохраняется. Поведение черновика «ошибка → False», при котором деталь молча пропадает из BOM, исключено.
- **REQ-RULE-04.** Опция, не выбранная в конфигурации, считается `False`.
- **REQ-RULE-05.** В UI правило показывается в нормализованном виде: ключевые слова — строчные, опции — заглавные.

### 7.4. Алгоритм конфигуратора
Вход: продукт `P`, дата `D` (по умолчанию — сейчас), набор опций `O` или имя конфигурации, флаг `include_drafts` (по умолчанию `false`).

1. **Проверка конфигурации.** Все опции из `O` существуют и активны, ограничения групп соблюдены. Иначе ошибка `INVALID_CONFIGURATION` со списком нарушений.
2. **Отбор позиций P.** Берутся позиции `product_line`, для которых `valid_from ≤ D < valid_to` (или `valid_to IS NULL`) и правило истинно на `O`.
3. **Разрешение ревизии потомка.** Берётся ревизия с максимальным `approved_at ≤ D` (статус Approved или Obsolete). Если `include_drafts = true` и ревизия In_Development существует, берётся она, а результат помечается «черновой». Если подходящей ревизии нет — ошибка позиции `NO_APPROVED_REVISION`.
4. **Рекурсивный разворот** по `structure_line` выбранной ревизии. Количество умножается по пути (`qty_total = qty_parent × qty_line`). Компоненты каталога — листья, ревизий не имеют. При обнаружении цикла — ошибка `CYCLE`.
5. **Свёртка и склейка MCAD/ECAD** (§8.6) по каждой составной части.
6. **Результат:**
   - `tree` — дерево с ревизиями, количествами, источниками и RefDes;
   - `flat` — плоский перечень по артикулам с суммарным количеством;
   - `warnings` — расхождения;
   - `errors` — ошибки; при их наличии результат помечен как недостоверный.
7. **REQ-CFG-01.** Результат воспроизводим: тот же вход (P, D, O) после любых последующих изменений даёт тот же 100% BOM, если `D` в прошлом и `include_drafts = false`.

## 8. Импорт составов

### 8.1. Общие правила
- **REQ-IMP-01.** Все импорты принимаются в едином формате (§8.5): источник, набор родительских сборок и их позиции. Источники различаются только адаптером.
- **REQ-IMP-02.** Импорт выполняется в режиме `dry_run` (только отчёт) или с применением. Применение атомарно: при любой ошибке не меняется ничего.
- **REQ-IMP-03.** Ошибки, блокирующие импорт:
  - обозначение похоже на артикул, но содержит кириллицу или нарушает маску (`GAС.BN.00007`);
  - артикул не найден в реестре;
  - у позиции нет ни артикула по маске, ни MPN;
  - у материала (`material_quantities`) нет компонента в каталоге или у экземпляра нет «Количества материала»;
  - нарушены правила вложенности;
  - обнаружен цикл;
  - дублируется RefDes внутри одного родителя.
- **REQ-IMP-04.** Для каждого родителя система сравнивает импортируемый состав с составом последней утверждённой ревизии, причём только позиции того же источника:
  - составы совпадают → «без изменений», ревизия не создаётся (импорт идемпотентен);
  - есть отличия и черновика нет → создаётся новая In_Development-ревизия (§6.1);
  - черновик уже есть → в нём заменяются позиции этого источника.
  Позиции других источников и ручные позиции (`MANUAL`) сохраняются.
- **REQ-IMP-05.** Импорт в утверждённую ревизию невозможен в принципе: импорт пишет только в черновик.
- **REQ-IMP-06.** Отчёт импорта по каждому родителю содержит:
  - действие: создана ревизия NN / обновлён черновик / без изменений;
  - дифф: добавлено / удалено / изменено количество / изменены RefDes;
  - ошибки и предупреждения.
- **REQ-IMP-07.** Импорт MCAD и ECAD выполняет роль Инженер.
- **REQ-IMP-08. Разрешение позиций.** Для MCAD и ECAD одинаково, по двум значениям: обозначению (КОМПАС — «Обозначение»; QElectroTech — Article number; Altium — Part) и MPN (КОМПАС — «Код продукции»; в ECAD — то же поле, что и обозначение):
  1. обозначение соответствует маске `xxY.zz.nnnnn` → собственный артикул (сборка, деталь, кабель, плата, доработанное изделие);
  2. обозначение похоже на маску, но с кириллицей или ошибкой → ошибка импорта;
  3. MPN есть в каталоге → компонент каталога;
  4. MPN не найден → компонент каталога создаётся автоматически по данным источника (описание, изготовитель, ед. изм. «шт», аналоги) и попадает в отчёт как «новый». Материалы автоматически не создаются (REQ-ART-08).
- **REQ-IMP-09. Импорт с релиза.** Ревизия схемы E и платы B создаётся только из релиза: тега git-репозитория, привязанного к артикулу (один репозиторий — одна схема или плата). При импорте указываются артикул и тег. Система сама забирает файлы этого коммита и сохраняет в ревизии репозиторий, тег и SHA коммита. Файлы ревизии — папка `doc/` релиза. Если доступа к репозиторию нет, тот же коммит можно загрузить архивом; SHA тогда указывается вручную.
- **REQ-IMP-10.** Один тег — не более одной ревизии артикула. Повторный импорт того же тега возвращает «без изменений». Формат тега релиза един для схем и плат: `vMAJOR.MINOR.PATCH` (регулярное выражение `^v\d+\.\d+\.\d+$`, например `v0.1.0`). Для плат тег совпадает с версией `HW x.y.z` на шелкографии. Тег другого формата отклоняется.
- **REQ-IMP-11.** Ревизию, созданную из релиза, утверждает Утверждающий (§6.3), как и любую другую. Тег означает готовность автора, а не утверждение в ЭСИ.

### 8.2. КОМПАС-3D (MCAD)
Свойства документов `.m3d`/`.a3d` (регламент для конструкторов):

| Свойство КОМПАС | Содержимое | Обязательность |
|---|---|---|
| Обозначение | Артикул `xxY.zz.nnnnn`, латиница | обязательно для собственных изделий; у покупных — любое значение не по маске (например, из библиотеки КОМПАС) или пусто |
| Наименование | Понятное русское название («Кронштейн двигателя»); для нового компонента каталога становится его описанием | обязательно |
| Код продукции | MPN или обозначение по стандарту (`DIN 912 M3x10 A2`) | обязательно для покупных |
| Поз. обозначение | RefDes экземпляра для мехатроники (`M1`) | необязательно, используется для сверки со схемой |
| Количество материала | Число в единице измерения компонента: `2.5` (м провода), `0.05` (кг клея) | обязательно для материалов (единица ≠ «шт») |

Изготовитель и аналоги покупного изделия заполняются в карточке компонента каталога в системе.

- **REQ-IMP-KOM-01.** Скрипт рекурсивно обходит активную сборку. Каждая подсборка передаётся как отдельный родитель со своим составом. Одинаковые подсборки обрабатываются один раз.
- **REQ-IMP-KOM-02.** Экземпляры одного компонента в пределах родителя агрегируются. Для позиции с единицей «шт» количество = числу вхождений. Для материала — компонента с единицей м, кг, м2 или л — количество = сумме свойства «Количество материала» по его экземплярам. Пример: два отрезка провода по 2,5 м дают 5 м. Экземпляр материала без этого свойства или с нечисловым значением — ошибка импорта с путём в дереве. Скрипт передаёт значения по каждому экземпляру (`material_quantities`), а единицу измерения определяет сервер по каталогу.
- **REQ-IMP-KOM-03.** Исключённые из расчёта компоненты пропускаются. Компоненты, у которых нет ни обозначения по маске, ни «Кода продукции», или с ошибочным обозначением (REQ-IMP-08, п. 2) попадают в отчёт об ошибках с путём в дереве сборки. Молча их отбрасывать нельзя: черновик скрипта так делал (`if not sku: continue`).
- **REQ-IMP-KOM-04.** Скрипт передаёт пользовательский токен, имя исходного файла и версию КОМПАС. Сначала выполняется `dry_run`, отчёт показывается конструктору, затем по подтверждению запрос повторяется с применением.
- **REQ-IMP-KOM-05.** Свойство «Источник данных» из черновика упраздняется: источник определяет сам импортёр.
- Эталон скрипта — [Приложение B](#Приложение%20B.%20Скрипт%20выгрузки%20из%20КОМПАС-3D).

### 8.3. QElectroTech (ECAD, схемы E)
Один проект QElectroTech — один репозиторий: файл `.qet` в корне, папка `doc/` (PDF листов, `parts list_*.csv`, `schematic_previews/`). Крупный объект делится на несколько проектов, например «исполнительные устройства и кабели» и «шкаф автоматики». Каждый проект — отдельный артикул E в составе продукта.

- **REQ-IMP-QET-01.** Источник — файл `.qet` из релиза. Для каждого элемента читаются поля Label, Article number, Manufacturer, Textual description, Quantity, Unity. Внутренние имена полей в XML фиксируются при реализации.
- **REQ-IMP-QET-02.** Элементы без Label пропускаются: так в QElectroTech устроены символы, не являющиеся объектом спецификации (символы клеммных блоков на листах схем и т.п.). Элемент с Label, но без Article number — ошибка импорта с указанием Label и листа.
- **REQ-IMP-QET-03.** Позиция разрешается по Article number (REQ-IMP-08). RefDes = Label (например, `2Q23`).
- **REQ-IMP-QET-04.** Количество позиции — сумма по её элементам: Quantity (если не заполнено — 1) в единицах Unity (`m` → `м`; пусто → `шт`). Пример: отрезной кабель `6 m` × 2 элемента = 12 м.
- **REQ-IMP-QET-05.** Ответные разъёмы плат (из `ext_bom.csv`, §8.4) входят в ЭСИ через схему: электроник вносит их в проект QElectroTech вручную.

### 8.4. Altium (ECAD, платы B)
Одна плата — один репозиторий: `hardware/` (проект Altium), `doc/pcb/` (производственный пакет: `Bill of Materials-*.csv`, `board_options.txt`, `gerber/`, `Pick Place *.csv`, PDF), `doc/drawing/` (3D-модель), `doc/photo/`, `doc/pinout/`. Версия платы `HW x.y.z` на шелкографии совпадает с тегом релиза.

- **REQ-IMP-ALT-01.** Источник — `doc/pcb/Bill of Materials-*.csv` из релиза: кодировка cp1251, разделитель `,`, колонки `Description, Comment, Designator, Footprint, Part, Alternative Part, JLCPCB Part, Quantity`. Пустая строка сразу после заголовка допускается, другие пустые строки — ошибка.
- **REQ-IMP-ALT-02.** Строки с Footprint `M3`–`M6` (крепёжные отверстия) не являются позициями и пропускаются.
- **REQ-IMP-ALT-03.** Позиция разрешается по Part (REQ-IMP-08). Alternative Part → аналоги, Description → описание, Comment, Footprint, JLCPCB Part → атрибуты компонента. Изготовителя в BOM Altium нет — он дополняется в карточке компонента.
- **REQ-IMP-ALT-04.** RefDes — список из Designator. Ошибки импорта: Quantity ≠ числу Designator в строке; пустые Part, Description или Designator; повтор одного Part в разных строках.
- **REQ-IMP-ALT-05.** `doc/pcb/board_options.txt` (TOML: размеры, тип, слои, покрытие, цвета маски и маркировки, толщины, число точек пайки, признак `ext_bom`) разбирается и сохраняется в параметры ревизии. Голая плата отдельным артикулом не заводится: B — смонтированная плата, а параметры платы и gerber-файлы относятся к её ревизии.
- **REQ-IMP-ALT-06.** `ext_bom.csv` (ответные разъёмы и фурнитура) в состав платы **не импортируется**: он нужен для заказа прототипа и хранится как файл ревизии. Ответные части попадают в ЭСИ через схему (REQ-IMP-QET-05).

### 8.5. Универсальный формат (CSV / JSON)
`POST /api/v1/import`:

```json
{
  "source_system": "MCAD",
  "tool": "KOMPAS-3D v23",
  "source_file": "GAA.GF.00534.a3d",
  "dry_run": true,
  "assemblies": [
    {
      "parent_sku": "GAA.GF.00534",
      "lines": [
        {"child_sku": "GAD.32.00002", "quantity": 4},
        {"child_sku": "GAC.BN.00007", "quantity": 2, "material_quantities": [2.5, 2.5]},
        {"mpn": "17HS4401", "description": "Двигатель шаговый NEMA17", "quantity": 2, "ref_des": ["M1", "M2"]},
        {"child_sku": "Винт DIN 912 M3x10", "mpn": "DIN 912 M3x10 A2", "quantity": 16},
        {"mpn": "RC0603FR-0710KL", "manufacturer": "YAGEO", "description": "Резистор 10 кОм 0603",
         "quantity": 3, "uom": "шт", "ref_des": ["R1", "R2", "R5"]}
      ]
    }
  ]
}
```
`source_system` ∈ {`MCAD`, `ECAD_QET`, `ECAD_ALTIUM`, `GENERIC`}. Позиция задаётся `child_sku` (обозначение) и/или `mpn` и разрешается по REQ-IMP-08. Необязательное поле `material_quantities` — значения «Количества материала» по экземплярам (REQ-IMP-KOM-02). CSV-вариант содержит колонки `parent_sku; child_sku; mpn; manufacturer; description; quantity; uom; ref_des`, где RefDes перечисляются через запятую.

### 8.6. Склейка MCAD и ECAD
Мехатронный компонент (например, шаговый двигатель `17HS4401`) есть и в 3D-модели, и на схеме. Обе записи разрешаются в один компонент каталога по MPN: в MCAD — по «Коду продукции», в ECAD — по Article number или Part (REQ-IMP-08). При свёртке 100% BOM (§7.4, шаг 5) по каждой позиции:

- **REQ-REC-01.** Если позиция пришла только из одного источника, количество суммируется.
- **REQ-REC-02.** Если позиция пришла и из MCAD, и из ECAD:
  - количество берётся **только из MCAD**: конструктор физически разместил устройства на раме;
  - RefDes собираются **из ECAD** (отсортированное объединение, вывод `M1, M2`).
  Правило действует для любого типа. Черновик описывал его для E/B/C и предлагал безусловное суммирование для D/A, что приводило бы к двойному счёту, если D/A оказались на схеме. Появление D/A в ECAD даёт предупреждение.
- **REQ-REC-03.** Предупреждения о расхождениях BOM не блокируют:
  - `QTY_MISMATCH` — количество по MCAD ≠ числу RefDes по ECAD;
  - `ECAD_ONLY` — компонент с признаком «мехатроника» (REQ-ART-08) есть на схеме, но нет в модели продукта. Для остальных компонентов каталога наличие только в ECAD — норма, предупреждение не выдаётся;
  - `MCAD_ONLY` — компонент с признаком «мехатроника» есть в модели, но ни на одной схеме продукта его нет;
  - `REFDES_MISMATCH` — поля «Поз. обозначение» в MCAD заполнены и не совпадают с RefDes из ECAD.
- **REQ-REC-04.** Ручные позиции (`MANUAL`) всегда суммируются со всеми остальными.

## 9. Выгрузки и отчёты

### 9.1. 100% BOM
- **REQ-EXP-01.** Дерево и плоский перечень (§7.4) в форматах JSON и CSV. В заголовке: продукт, дата, опции, признак «черновой», время формирования.
- **REQ-EXP-02.** Колонки плоского перечня:
  - артикул или MPN, наименование, тип, ревизия;
  - количество, единица измерения;
  - изготовитель, аналоги (для компонентов каталога);
  - RefDes, предупреждения.

  Компоненты каталога выводятся теми же строками: вместо артикула и ревизии у них MPN, тип — «компонент».

### 9.2. «Где используется» (where-used)
- **REQ-EXP-03.** Для артикула выводятся все ревизии родителей, в составе которых он есть, и цепочка вверх до продуктов P. Для каждого P указываются интервалы применимости и правила. Это основа будущего анализа влияния изменений (этап 3).

## 10. REST API

Базовый путь — `/api/v1`. В пути используется артикул, внутренние `id` наружу не публикуются. Авторизация — `Authorization: Bearer <token>`.

| Метод и путь | Назначение |
|---|---|
| `GET /projects`, `GET /projects/{xx}/groups?type=` | Справочники |
| `POST /items` | Создать артикул `{project, type, group, name, uom, base_component?, …}` → `display_sku` |
| `GET /items?q=&type=&project=&group=` | Поиск по артикулу и наименованию |
| `GET /components?q=`, `POST /components`, `GET/PATCH /components/{mpn}`, `GET /components/{mpn}/where-used` | Каталог компонентов (REQ-ART-08): поиск по MPN и описанию, ручное создание (материалы) |
| `GET /items/next-number?project=&type=&group=` | Предпросмотр следующего номера, без резервирования |
| `GET /items/{sku}`, `PATCH /items/{sku}` | Карточка; изменение атрибутов, кроме составляющих артикула |
| `GET /items/{sku}/where-used` | §9.2 |
| `POST /items/{sku}/revisions` | Создать ревизию In_Development (§6.1) |
| `GET /items/{sku}/revisions/{rev}` | Ревизия с составом и файлами |
| `POST /items/{sku}/revisions/{rev}/approve` | Утвердить `{comment, notice_number}` |
| `POST/GET /items/{sku}/revisions/{rev}/files`, `GET …/files/{file_id}` | Загрузка, перечень, скачивание файлов |
| `PUT /items/{sku}/revisions/{rev}/lines` | Ручные позиции `MANUAL` в черновике |
| `POST /import` | Универсальный импорт (§8.5) |
| `POST /import/qet`, `POST /import/altium` | Импорт из релиза `{parent_sku, tag, dry_run}` или из архива коммита (multipart + `commit_sha`) (REQ-IMP-09) |
| `GET/POST /products/{sku}/lines`, `POST /products/{sku}/lines/{id}/replace`, `POST …/close` | Состав продукта P (§7.2) |
| `GET/POST/PATCH /products/{sku}/options`, `…/option-groups`, `…/configurations` | Опции и конфигурации |
| `POST /rules/validate` | Проверка правила `{product_sku, rule}` |
| `GET /bom/configured?sku=&date=&options=A,B&config=&view=flat\|tree&include_drafts=` | 100% BOM (§7.4) |

- **REQ-API-01.** Ошибки возвращаются в едином формате `{code, message, details[]}`. Коды: `VALIDATION_ERROR`, `NOT_FOUND`, `FORBIDDEN`, `CONFLICT` (например, черновик уже существует), `IMMUTABLE` (попытка изменить утверждённое), `INVALID_CONFIGURATION`, `IMPORT_FAILED`.
- **REQ-API-02.** Схема публикуется в OpenAPI (`/docs`).

## 11. Пользовательский интерфейс и утилиты (MVP)

- **REQ-UI-01. Реестр.** Поиск и фильтры по проекту, типу, группе и статусу. Карточка артикула: ревизии (для E/B — тег, коммит, параметры платы), файлы, состав, «где используется», журнал. Каталог компонентов с поиском по MPN и описанию.
- **REQ-UI-02. Генератор артикулов.** Пользователь выбирает проект, тип и группу (в списке только группы выбранного типа) и видит следующий номер. Кнопка «Создать» резервирует артикул и копирует его в буфер обмена. Кнопка «Создать ещё в той же группе» повторяет действие без повторного выбора.
- **REQ-UI-03. Редактор продукта P.** Таблица позиций с правилами и интервалами, переключатель «показать на дату», операция «Заменить позицию» (§7.2), редактор правил с подсказкой опций и проверкой на лету.
- **REQ-UI-04. Конфигуратор.** Выбор опций с соблюдением групп и даты, просмотр дерева и плоского 100% BOM с предупреждениями, выгрузка CSV/JSON.
- **REQ-UI-05. Импорт.** Загрузка файла или приём из скрипта, отчёт dry-run с диффом, подтверждение.
- **REQ-UI-06.** Интерфейс на русском языке. Коды статусов на английском хранятся в БД, в UI выводятся русские подписи: «В разработке», «Утверждено», «Заменено».

## 12. Нефункциональные требования

- **REQ-NF-01. Стек.** Backend на Python 3.12+ с генерацией OpenAPI, PostgreSQL 16+, версионируемые миграции схемы. Развёртывание через Docker Compose.
- **REQ-NF-02. Хранилище файлов** (решение D8). Абстракция с двумя реализациями: локальный диск и S3-совместимое хранилище (MinIO). Файлы адресуются ключом и SHA-256, повторная загрузка того же содержимого не дублирует данные. Ограничение размера файла настраивается (по умолчанию 500 МБ).
- **REQ-NF-03. Безопасность.** HTTPS. Аутентификация через OpenLDAP (LDAPS или StartTLS), пароли в системе не хранятся. API-токены выдаются в системе пользователю из LDAP и хранятся только в виде хеша. При блокировке пользователя в LDAP его токены перестают действовать. Роли проверяются на каждом эндпоинте.
- **REQ-NF-04. Аудит.** Все изменяющие операции пишутся в `audit_log`. Журнал не редактируется через API.
- **REQ-NF-05. Резервное копирование.** Ежедневный дамп БД и копия хранилища файлов, хранение 30 дней. Процедура восстановления описана и проверена.
- **REQ-NF-06. Производительность.** Нагрузка: 10 пользователей на старте, до 20 в перспективе; около 100 продуктов P. Расчёт 100% BOM для продукта с 5 000 развёрнутых позиций и глубиной вложенности до 10 занимает не более 3 с. Поиск по реестру — не более 300 мс.
- **REQ-NF-08. Доступ к git.** Репозитории схем и плат могут находиться и на GitHub, и на GitLab, включая self-hosted. Система читает их по HTTPS с токеном доступа только на чтение. Администратор задаёт токены для каждого хоста (например, `github.com`, `gitlab.<домен>`); токены хранятся в секретах развёртывания и не выводятся через API и UI. Хост определяется по `repo_url` артикула. Ошибка доступа возвращается в отчёте импорта с указанием хоста.
- **REQ-NF-07. Тесты.** Модульные тесты парсера правил, конфигуратора, склейки MCAD/ECAD и счётчика номеров, включая параллельную выдачу. Интеграционные тесты API на тестовой БД.

## 14. Критерии приёмки (сквозной сценарий MVP)

1. Администратор создаёт проект `GA` и группы `GF`, `32`, `AV`, `ZY`, `A1`.
2. Инженер создаёт через генератор `GAD.32.00000` и `GAD.32.00001`. Два параллельных запроса на создание дают разные номера. Администратор создаёт `GAD.32.00004` с ручным номером; следующие запросы генератора выдают `00002`, `00003`, `00005`.
3. В каталоге заводится двигатель `17HS4401` с изготовителем, а также материал «Провод ПуГВ 0,75» с единицей «м». Повторное создание компонента с тем же MPN (в том числе ` 17hs4401 `) отклоняется.
4. Попытка создать `GAС.BN.00007` с кириллической «С» отклоняется с понятным сообщением.
5. Сборка `GAA.GF.00534` импортируется из КОМПАС: 2 детали ×4, двигатель ×2 (по «Коду продукции» `17HS4401`, получает признак «мехатроника»), винт `DIN 912 M3x10 A2` ×16 (создаётся в каталоге автоматически), провод 2 × 2,5 м = 5 м. Dry-run показывает дифф, применение создаёт ревизию `01` In_Development. Повторный импорт без изменений возвращает «без изменений».
6. Утверждение ревизии `01` без файлов отклоняется. После загрузки файла ревизия утверждается. Изменить её состав нельзя — ответ `IMMUTABLE`.
7. Схема `GAE.AV.00001` импортируется из QElectroTech с тега `v1.0.0`. На схеме двигатель с Article number `17HS4401` и Label `M1`, `M2` — он разрешается в тот же компонент каталога, что и в MCAD. Автомат с новым MPN автоматически попадает в каталог. Элемент с Label без Article number блокирует импорт. В ревизии сохранены тег и SHA коммита, файлы — `doc/` релиза. Повторный импорт того же тега возвращает «без изменений». Ревизия утверждается.
8. Плата `GAB.ZY.10000` импортируется из Altium с тега `v1.0.0`. Строки крепёжных отверстий (`M3`) пропускаются, компоненты попадают в каталог, `board_options.txt` — в параметры ревизии, `ext_bom.csv` — только в файлы. Ревизия утверждается.
9. Создаётся продукт `GAP.A1.00001` с опциями `WINTER_PACK`, `CHIP_V2` и позициями:
   - `GAA.GF.00534` без правила;
   - `GAE.AV.00001` без правила;
   - плата `GAB.ZY.10000` с правилом `WINTER_PACK and not CHIP_V2`.
   Правило `WINTER_PAK` (опечатка) не сохраняется.
10. 100% BOM при `{WINTER_PACK}` содержит плату и её компоненты каталога. Двигатель ×2 (количество из MCAD) с RefDes `M1, M2`, без предупреждений. При `{}` платы нет.
11. Плата заменяется операцией «Заменить позицию» с даты `T`: старая — `WINTER_PACK and not CHIP_V2` до `T`, новая `GAB.ZY.10001` — `WINTER_PACK` с `T`. 100% BOM на дату до `T` совпадает с шагом 10 (воспроизводимость), после `T` содержит новую плату.
12. «Где используется» для компонента `17HS4401` показывает `GAA.GF.00534 rev 01` → `GAP.A1.00001` и `GAE.AV.00001 rev 01` → `GAP.A1.00001`.
13. Все изменяющие действия шагов 1–11 есть в журнале.

## 16. План первичного наполнения

Готового реестра нет, поэтому данные не переносятся, а наполняются заново по действующей документации. Наполнение идёт **снизу вверх**: детали и покупные → сборки → схемы и платы → продукт. Так к моменту импорта родителя все его потомки уже есть в реестре (REQ-IMP-03).

### 16.1. Принципы
- **REQ-MIG-01.** Наполнение выполняется штатными средствами системы: генератор, импорт, редактор продукта. Прямая запись в БД не используется: это одновременно проверяет MVP на реальных данных.
- **REQ-MIG-02.** Изделия, у которых уже есть артикул по маске (нанесён на детали или стоит в «Обозначении»), сохраняют его: Администратор создаёт их с явным номером (REQ-ART-04). Остальным артикул выдаёт генератор.
- **REQ-MIG-03.** Истории изменений нет. Все стартовые позиции продуктов получают `valid_from` = дата ввода продукта в систему, ревизия всех составных частей — `01`. Ревизия E и B — текущий релиз репозитория.
- **REQ-MIG-04.** Продукт считается наполненным, когда его 100% BOM для каждой выпускаемой комплектации сверен с реально собранным экземпляром или с действующей спецификацией и расхождений нет (или они объяснены и исправлены).

### 16.2. Этап 0. Подготовка
| # | Действие | Ответственный | Результат |
|---|---|---|---|
| 0.1 | Развернуть систему, подключить OpenLDAP, создать группы LDAP для ролей | Администратор | Пользователи входят со своими учётными записями |
| 0.2 | Завести токены чтения для GitHub и GitLab | Администратор | Проверочный импорт из любого репозитория проходит |
| 0.3 | Составить перечень продуктов: ~100 позиций, по каждому — сборки КОМПАС, репозитории схем и плат, выпускаемые комплектации | Ведущие конструктор и электроник | Таблица-реестр наполнения: продукт → источники → ответственный |
| 0.4 | Утвердить справочник проектов `xx` и групп `zz` по каждому типу | Ведущие инженеры + Администратор | Справочники заполнены в системе |
| 0.5 | Ввести регламент свойств КОМПАС (§8.2), включая «Код продукции» для покупных и «Количество материала»; обновить шаблоны деталей и сборок | Ведущий конструктор | Шаблоны со всеми свойствами |
| 0.6 | Выпустить скрипт выгрузки из КОМПАС (Приложение B) на рабочие места конструкторов, выдать API-токены | Администратор | Скрипт выполняет dry-run |
| 0.7 | Выбрать пилотный продукт: в нём должны быть механика, мехатроника (мотор или датчик), схема QElectroTech, плата Altium и хотя бы две комплектации | Руководитель внедрения | Пилот выбран |

### 16.3. Этап 1. Пилот (один продукт)
1. **Детали и покупные MCAD.** Для каждой детали D из сборок пилота выдать артикул в генераторе и вписать его в «Обозначение». У покупных изделий заполнить «Код продукции» (MPN или обозначение по стандарту) — артикул им не нужен. Материалы завести в каталоге с единицей измерения и заполнить у их экземпляров «Количество материала».
2. **Сборки.** Выдать артикулы сборкам A и вписать их в «Обозначение». Запустить скрипт на верхней сборке: он передаёт все подсборки (REQ-IMP-KOM-01). Исправить все ошибки dry-run, применить импорт. Загрузить файлы ревизий.
3. **Схемы.** Завести артикулы E, указать `repo_url`. Привести проект к qguide: у каждого элемента с Label заполнен Article number. Мехатронику указать тем же MPN, что в «Коде продукции» в КОМПАС. Поставить тег `vX.Y.Z` на текущий релиз (если релиз был помечен «release v0.1.0» — перевыпустить как `v0.1.0`). Импортировать.
4. **Платы.** Завести артикулы B, указать `repo_url`, поставить тег, равный `HW x.y.z` на шелкографии. Импортировать. Новые компоненты попадут в каталог автоматически — дополнить в каталоге производителей.
5. **Утверждение.** Утверждающий проверяет и утверждает ревизии `01` всех составных частей пилота.
6. **Продукт.** Создать продукт P, словарь опций и группы опций, позиции 150% состава с правилами (`valid_from` = дата ввода). Для каждой выпускаемой комплектации сохранить конфигурацию.
7. **Сверка (REQ-MIG-04).** Построить 100% BOM каждой конфигурации и сверить с реальным изделием. Отдельно разобрать предупреждения склейки (§8.6). Исправления делать в источниках (КОМПАС, схема, плата) и импортировать повторно, а не править вручную.
8. **Разбор пилота.** Зафиксировать ошибки ТЗ и регламентов, сроки по шагам и типовые проблемы. Скорректировать регламенты и, при необходимости, ТЗ. По фактическим срокам пилота спланировать волны этапа 2.

**Критерий выхода:** пилотный продукт наполнен по REQ-MIG-04, найденные дефекты системы исправлены или внесены в план.

### 16.4. Этап 2. Волны наполнения
- **REQ-MIG-05.** Остальные продукты наполняются волнами по шагам 1–7 пилота. Порядок волн — по перечню 0.3: сначала продукты в текущем производстве, затем продукты с общими сборками (их модули уже будут в реестре), затем остальные.
- **REQ-MIG-06.** Общие сборки, схемы и платы наполняются один раз — в первой волне, где они встретились. Следующие волны на них только ссылаются.
- **REQ-MIG-07.** Прогресс ведётся в таблице-реестре наполнения (0.3): статус продукта «не начат / в работе / сверен» и ответственный.

### 16.5. Этап 3. Переход
- **REQ-MIG-08.** С даты перехода, которую объявляет руководитель внедрения после пилота, новые артикулы выдаются **только** генератором системы. Для продуктов в работе это действует сразу, независимо от волны.
- **REQ-MIG-09.** После наполнения всех продуктов из перечня 0.3 система становится единственным источником состава изделий. Составы вне системы (таблицы, ручные спецификации) не используются.

### 16.6. Риски наполнения
| Риск | Мера |
|---|---|
| В сборках КОМПАС нет единого «Обозначения» и свойств | Шаблоны 0.5; dry-run показывает все проблемы сразу, с путями в дереве |
| Мехатроника в схеме и модели обозначена по-разному | Шаг 3: в схеме указывается тот же MPN, что в КОМПАС; предупреждения `QTY_MISMATCH`, `ECAD_ONLY`, `MCAD_ONLY` |

Выдача номера (REQ-ART-03), выполняется в одной транзакции с `INSERT INTO item_master`:

```sql
INSERT INTO item_counter (project_code, item_type, group_code)
VALUES (:p, :t, :g) ON CONFLICT DO NOTHING;

SELECT next_number FROM item_counter                 -- блокировка до конца транзакции;
 WHERE project_code = :p AND item_type = :t AND group_code = :g
   FOR UPDATE;                                       -- ручное создание (REQ-ART-04) берёт ту же блокировку

SELECT min(n) AS sequence_number                     -- наименьший свободный номер ≥ счётчика
  FROM generate_series(:next_number, 99999) AS n
 WHERE NOT EXISTS (
       SELECT 1 FROM item_master m                   -- логически удалённые тоже занимают номер
        WHERE m.project_code = :p AND m.item_type = :t
          AND m.group_code = :g AND m.sequence_number = n);
-- NULL → ошибка «группа исчерпана»

UPDATE item_counter SET next_number = :sequence_number + 1
 WHERE project_code = :p AND item_type = :t AND group_code = :g;
```

## Приложение B. Скрипт выгрузки из КОМПАС-3D

Эталон логики: рекурсия, агрегация, отчёт об ошибках, dry-run, токен. Вызовы API КОМПАС вынесены в функции `kompas_*`; их нужно сверить с SDK используемой версии КОМПАС (API7).

```python
import os
import sys
from collections import defaultdict

import requests
from win32com.client import Dispatch

PLM_API_URL = os.environ.get("PLM_API_URL", "http://localhost:8000/api/v1/import")
PLM_TOKEN = os.environ["PLM_TOKEN"]
PROP_REFDES = "Поз. обозначение"
PROP_MATERIAL_QTY = "Количество материала"
PROP_PRODUCT_CODE = "Код продукции"


# --- Обёртки API КОМПАС (сверить с SDK) -------------------------------------
def kompas_connect():
    return Dispatch("KOMPAS.Application.7")


def kompas_top_part(app):
    doc = app.ActiveDocument
    if doc is None or not doc.FileName.lower().endswith(".a3d"):
        sys.exit("[-] Откройте сборку (.a3d) в КОМПАС-3D")
    return doc.TopPart, doc.FileName


def kompas_children(part):
    parts = part.Parts
    return [parts.Part(i) for i in range(parts.Count)]


def kompas_is_assembly(part):
    return not part.Detail


def kompas_is_excluded(part):
    return bool(getattr(part, "Excluded", False))


def kompas_marking(part):
    return (part.Marking or "").strip()


def kompas_property(part, name):
    # TODO: чтение пользовательского свойства через IPropertyMng / IPropertyKeeper
    return None


def kompas_refdes(part):
    return kompas_property(part, PROP_REFDES)


def kompas_product_code(part):
    return (kompas_property(part, PROP_PRODUCT_CODE) or "").strip()


def kompas_material_qty(part):
    value = kompas_property(part, PROP_MATERIAL_QTY)
    return float(str(value).replace(",", ".")) if value not in (None, "") else None


# --- Обход сборки -----------------------------------------------------------
def collect(top_part):
    assemblies = {}          # parent_sku -> {(обозначение, MPN): строка состава}
    errors = []

    def walk(part, path):
        parent_sku = kompas_marking(part)
        if parent_sku in assemblies:
            return           # одинаковые подсборки обрабатываются один раз
        lines = {}
        assemblies[parent_sku] = lines
        for child in kompas_children(part):
            if kompas_is_excluded(child):
                continue
            marking = kompas_marking(child)
            mpn = kompas_product_code(child)
            child_path = f"{path} / {child.Name}"
            if not marking and not mpn:
                errors.append(f"Нет ни обозначения, ни кода продукции: {child_path}")
                continue
            line = lines.setdefault((marking, mpn), {
                "child_sku": marking or None, "mpn": mpn or None, "description": child.Name,
                "quantity": 0, "ref_des": [], "material_quantities": [],
            })
            line["quantity"] += 1
            try:
                line["material_quantities"].append(kompas_material_qty(child))
            except ValueError:
                errors.append(f"Нечисловое «{PROP_MATERIAL_QTY}»: {child_path}")
            refdes = kompas_refdes(child)
            if refdes:
                line["ref_des"].append(refdes)
            if kompas_is_assembly(child):
                walk(child, child_path)

    walk(top_part, kompas_marking(top_part))
    return assemblies, errors


def build_payload(assemblies, source_file, dry_run):
    return {
        "source_system": "MCAD",
        "tool": "KOMPAS-3D",
        "source_file": os.path.basename(source_file),
        "dry_run": dry_run,
        "assemblies": [
            {"parent_sku": parent,
             "lines": list(lines.values())}
            for parent, lines in assemblies.items()
        ],
    }


def send(payload):
    resp = requests.post(PLM_API_URL, json=payload, timeout=60,
                         headers={"Authorization": f"Bearer {PLM_TOKEN}"})
    resp.raise_for_status()
    return resp.json()


if __name__ == "__main__":
    top, file_name = kompas_top_part(kompas_connect())
    assemblies, errors = collect(top)
    if errors:
        print("[-] Ошибки в модели:\n  " + "\n  ".join(errors))
        sys.exit(1)
    report = send(build_payload(assemblies, file_name, dry_run=True))
    print(report)          # дифф и ошибки валидации сервера
    if input("Применить? [y/N] ").lower() == "y":
        print(send(build_payload(assemblies, file_name, dry_run=False)))
```

Невалидные обозначения (маска, кириллица, неизвестный артикул) и отсутствующее «Количество материала» у материалов проверяет сервер и возвращает в отчёте dry-run.

## Приложение C. Грамматика правил применимости

```ebnf
rule     = [ or_expr ] ;                       (* пустое правило = всегда *)
or_expr  = and_expr , { "or" , and_expr } ;
and_expr = not_expr , { "and" , not_expr } ;
not_expr = "not" , not_expr | atom ;
atom     = OPTION | "(" , or_expr , ")" ;
OPTION   = [A-Z] , { [A-Z0-9_] } ;             (* кроме AND, OR, NOT *)
(* ключевые слова and/or/not — без учёта регистра; приоритет: not > and > or *)
```

| Правило | `{WINTER_PACK}` | `{WINTER_PACK, CHIP_V2}` | `{}` |
|---|---|---|---|
| *(пусто)* | ✔ | ✔ | ✔ |
| `WINTER_PACK` | ✔ | ✔ | ✘ |
| `WINTER_PACK and not CHIP_V2` | ✔ | ✘ | ✘ |
| `WINTER_PACK AND CHIP_V2` | ✘ | ✔ | ✘ |
| `not (WINTER_PACK or CHIP_V2)` | ✘ | ✘ | ✔ |
| `WINTER_PAK` (нет в словаре) | ошибка при сохранении | | |
| `WINTER_PACK and` | ошибка синтаксиса при сохранении | | |

### Пример: замена платы подогрева `GAB.ZY.10000`
- **Замена для всех будущих «зимних пакетов»** (применимость по дате): старая плата — правило `WINTER_PACK`, `valid_to = 2026-09-29`; новая `GAB.ZY.10001` — правило `WINTER_PACK`, `valid_from = 2026-09-29`. Выполняется одной операцией «Заменить позицию».
- **Замена при смене поставщика чипов** (уточнение правила): к продукту добавляется опция `CHIP_V2`, старая позиция закрывается и открывается заново с правилом `WINTER_PACK and not CHIP_V2`, новая плата — `WINTER_PACK and CHIP_V2`. Механика и другие позиции не затрагиваются.
